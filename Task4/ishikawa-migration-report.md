# Task4 — Узкие места миграции (по диаграмме Исикавы)

Цель миграции — уйти от текущего «файлового» и разрозненного ландшафта к сервисной архитектуре без просадки по производительности и без потери контроля над чувствительными данными.

## 1. Где главные риски

| Категория | Что может стать узким местом | Приоритет |
|---|---|---|
| Инфраструктура | Один периметр и слабая отказоустойчивость | P1 |
| ПО | Сложная декомпозиция legacy-логики | P1 |
| Интеграция | Нестабильные/неформализованные обмены с 1С | P1 |
| Данные | Разнородные источники и слабый data lineage | P1 |
| Персонал | Недостаток платформенных и security-компетенций | P2 |
| Процессы | Слабые quality gates и change management | P2 |

## 2. Что делаем в первую очередь

1. P1: Вводим отдельный интеграционный слой (anti-corruption layer) для 1С и внешних API.
2. P1: До активной миграции закрываем базу по безопасности: IAM, аудит, шифрование C3+.
3. P1: Формируем data catalog + tagging и нормализуем качество исходных данных.

## 3. Что делаем вторым эшелоном

1. P2: Мигрируем по доменам, а не «большим взрывом» (запись -> клиника -> биллинг).
2. P2: Добавляем quality gates в CI/CD (security, privacy, performance).
3. P2: На каждую волну миграции запускаем нагрузочные тесты и контроль SLI/SLO.

## 4. Организационные меры

1. P3: Усиливаем команду ролями platform/data/security.
2. P3: Планируем обучение сотрудников новым процессам и инструментам.

## 5. Как поймем, что миграция идет правильно

1. Ручные операции в критичных процессах заметно снижаются.
2. Инциденты доступа к C3+ данным не растут, а идут вниз от квартала к кварталу.
3. Доступность ключевых сценариев удерживается в целевых SLO.
4. Скорость поставки изменений не падает при росте нагрузки.

## 6. Вывод

Основной риск не в одном компоненте, а в связке: legacy-интеграции + качество данных + зрелость процессов.
Поэтому стратегия миграции должна быть поэтапной, с ранним внедрением privacy/security-контуров и постоянной проверкой результатов по метрикам.
