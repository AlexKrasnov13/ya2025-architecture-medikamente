# Task1 — Анализ безопасности системы (As-Is)

## Что именно считаем чувствительными данными

В текущем процессе обрабатываются несколько классов данных, которые требуют разного уровня защиты:

1. **Базовые персональные данные**: ФИО, дата рождения, телефон, email.
2. **Расширенные ПДн**: адрес, место работы или учёбы.
3. **Медицинские данные**: жалобы, анамнез, диагнозы, назначения, результаты анализов, заключения.
4. **Юридически значимые данные**: договоры, согласия, история обращений.
5. **Платёжные данные**: услуги, суммы, чеки, статус оплат.
6. **Служебные данные безопасности**: логи доступа, журналы действий сотрудников.

## Где сейчас основные риски

Ниже — ключевые слабые места текущего состояния (As-Is):

1. Чувствительные данные лежат в Excel/JPG/PDF на общем диске.
2. Нет сквозного аудита операций с критичными данными.
3. Нет единой классификации и тегирования данных.
4. На практике не реализована минимизация данных.
5. Файловый режим 1С и ручной double-entry увеличивают риск ошибок и утечек.
6. Нет формальной retention/deletion policy.
7. Передача данных между системами не нормализована и слабо контролируется.
8. Отсутствует RBAC/ABAC на уровне медзаписей и отдельных полей.
9. В релизном процессе нет автоматических security/privacy quality gates.
10. Единый локальный сервер в офисе создаёт риск SPOF и проблем с доступностью.

## Насколько это соответствует базовым практикам

| Практика | Статус As-Is | Что не хватает |
|---|---|---|
| Privacy by Design | Частично | Нет встроенных privacy-контролей в разработке и эксплуатации |
| Data Minimization | Низкий | В ручных процессах собираются и хранятся лишние поля |
| Data Lineage | Низкий | Не описано формально, откуда и куда движутся данные |
| Least Privilege | Низкий | Права не привязаны к объекту и контексту доступа |
| Accountability | Низкий | Нет централизованного неизменяемого аудита |

## Что именно защищаем и как

| Класс данных | Примеры | Основные меры защиты |
|---|---|---|
| Идентификационные ПДн | ФИО, телефон, email | Шифрование at rest, TLS in transit, маскирование в UI/отчётах |
| Медицинские данные | Диагнозы, анализы, заключения | Шифрование at rest, ABAC по контексту, токенизация/псевдонимизация для аналитики |
| Платёжные данные | Чеки, суммы, операции | Шифрование at rest/in transit, разделение обязанностей, контроль выгрузок |
| Договорные документы | Согласия, договоры | Шифрование, контроль сроков хранения, DLP |
| Аудиторские логи | Доступ/изменения данных | WORM/immutable storage, контроль целостности, SIEM |

## Что делаем в первую очередь

### P1 (критично)

1. Ввести модель тегирования данных и обязательную маркировку полей в API и БД.
2. Внедрить IAM (RBAC + ABAC) по принципу наименьших привилегий.
3. Сделать централизованный аудит с алертингом аномалий доступа.
4. Включить шифрование at rest для БД/бэкапов/файлов и TLS/mTLS in transit.

### P2 (важно)

1. Уйти от общего файлового хранилища к сервисам с контролируемым доступом.
2. Внедрить DLP для почты/выгрузок и согласование массовых выгрузок.
3. Утвердить retention/deletion policy и процесс обработки запросов субъектов ПДн.

### P3 (доработки)

1. Добавить policy-as-code проверки для tagged data в CI/CD.

## Механизм тегирования данных

### Набор тегов

1. `DATA_CLASS`: `PUBLIC`, `INTERNAL`, `CONFIDENTIAL`, `SPECIAL_MEDICAL`.
2. `SUBJECT_SCOPE`: `PATIENT_SELF`, `STAFF`, `AGGREGATED`.
3. `LEGAL_BASIS`: `CONTRACT`, `CONSENT`, `LEGAL_OBLIGATION`.
4. `RETENTION`: `30D`, `1Y`, `5Y`, `PER_REGULATION`.
5. `ACCESS_POLICY`: идентификатор policy для RBAC/ABAC.

### Обязательные правила применения

1. Поля `SPECIAL_MEDICAL` доступны только через ABAC с проверкой цели доступа.
2. Поля `PATIENT_SELF` в клиентском ЛК выдаются только владельцу данных.
3. Для событий чтения/изменения `CONFIDENTIAL` и выше аудит обязателен.
4. Во внешние интеграции нельзя передавать прямые идентификаторы без юридического основания.

## Критерии приемки Task1

1. DFD As-Is и To-Be покрывают запись, прием, оплату и анализы.
2. Для каждого ключевого потока определены риски и контроли.
3. Есть явная карта данных для защиты и понятный механизм тегирования.
4. Есть приоритизированный и реалистичный список улучшений.
